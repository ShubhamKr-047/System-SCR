**1. Product decision and non-negotiable behavior**

Build a browser-extension coach that explains the idea behind a selected move using local Stockfish evidence and natural language generated by Groq. The user supplies their own Groq free-tier key. The application requires no paid backend, shared developer credential, or local language-model download.

The central interaction is **Explain**. An explicit click authorizes at most one Groq generation request for that selected move and explanation style. A cache hit, a directly explainable terminal outcome, missing credentials, insufficient evidence, or an active cooldown can result in zero requests. No automatic second request is allowed for repair, verification, model fallback, or retries.

Importing a game, reviewing it with Stockfish, selecting moves, playing a variation, flipping the board, saving a key, changing settings, opening the extension, and expanding an existing explanation must make zero Groq requests. Do not perform a hidden key-validation or model-discovery request on save. Retry or refresh must be explicit user actions governed by the same one-request rule.

Existing local Stockfish review may continue to analyze the game for classifications and the evaluation graph. That work consumes local compute, not Groq quota. Additional analysis specifically for a coaching explanation runs only after Explain and only for the requested position. There is no automatic whole-game AI review or explanation prefetch.

Support useful feedback for every legal reviewed move, including book, forced, ordinary, tactical, positional, and terminal moves. Do not promise that every position has a fully established causal explanation. A limited but accurate explanation is preferable to an invented reason.

**2. What changes and what stays**

Retain the board, PGN import, game tree, variation playback, bundled Stockfish integration, opening lookup, classification pipeline, and existing correct regression cases. Replace the coaching option-selector architecture. Groq will receive verified facts and comparisons, not a menu of complete sentences it must copy.

Retain the useful principles of legal replay, position provenance, local fallback, escaping output, cancellation, and evidence-aware caching. Extend those principles to support generated prose. Keep classification changes outside this redesign: coaching may flag unstable or contradictory evidence but must not silently overwrite move labels or evaluations.

Make Groq the only provider exposed by the redesigned coach. Remove Gemini request paths, settings, and host permission at final cutover after compatibility checks. Preserve existing saved Groq credentials through a deliberate migration; do not delete unrelated settings or credentials during development.

The working tree already contains edits to coaching, tests, and simulation files. Record the baseline and preserve those edits. Never reset or overwrite them as a way to start the redesign.

**3. User experience and request contract**

| User action or condition | Local behavior | Groq calls |
| --- | --- | --- |
| Import/review/navigate/flip/save key | Existing analysis and UI only | 0 |
| Explain with a compatible cached result | Display cached explanation and lines | 0 |
| Explain for a direct local outcome | Display factual local explanation | 0 |
| Explain without a key | Show local feedback and an optional setup link | 0 |
| Explain for an uncached eligible position | Prepare evidence, reserve quota, request once | At most 1 |
| Double-click Explain for the same job | Join the existing job | No additional call |
| Expand details/show line/compare moves | Reveal saved content or replay locally | 0 |
| Change player level | Update preference; retain old result until Explain | 0 |
| Response invalid, timeout, or server error | Show local fallback and manual retry control | No automatic call |
| Rate-limited | Show local feedback and cooldown | No automatic call |
| Retry after cooldown | Recheck state and evidence, then request once | At most 1 |

Show progress in meaningful stages: preparing the position, checking continuations, writing the explanation. Keep the board and engine line usable throughout. Preserve local feedback while the request is pending.

The explanation card contains a short main idea, optional comparison, optional lesson, and an expandable supporting line. Prefer roughly 30–70 words for ordinary moves and up to roughly 150 words across expanded content for complicated moves; tune these editorial targets with evaluation. Do not manufacture sections merely to fill a schema. Keep a larger technical response-size ceiling to handle abuse or malformed output.

Use White/Black or the moving side unless the user's side is known. Do not automatically call every move “your move.”

**4. Target architecture**

```text
Explain click + selected node + player level
    -> request coordinator captures position/history/version
    -> compatible persistent cache lookup
    -> local evidence preparation and bounded Stockfish comparisons
    -> local outcome or insufficient-evidence fallback, when appropriate
    -> compact report and token estimate
    -> extension-wide quota admission and final target check
    -> one Groq request
    -> structural and supported-claim checks
    -> cache validated result
    -> render only if the selected target still matches
```

Use a dedicated `src/coaching/` area rather than expanding `main.js` into the orchestration layer.

The exact number of files may shrink if responsibilities remain clear. Integrate the coordinator with `main.js`; reuse `engine.js`, `position-analysis.js`, and the game tree. Add a small background coordination interface only for cross-tab quota/duplicate protection. Heavy analysis and long network work remain owned by the review page, with jobs recoverable after interruptions.

**5. Evidence and comparison contract**

Capture an immutable request identity: root position, relevant move history, selected move, resulting position, classification revision, and analysis version. Legally reconstruct positions. FEN alone is insufficient for repetition-sensitive outcomes.

Prepare evidence from three sources:

- Direct facts: legal moves, captures, checks, board relationships, terminal states, material balances, and changes in piece placement.
- Engine-supported findings: best replies, alternative moves, evaluation differences, compensation, and continuation outcomes.
- Strategic interpretations: possible explanations of activity, coordination, pawn structure, or king exposure, with explicit uncertainty when causality is not established.

For a selected move, compare the played move against the strongest alternative and, when useful, one plausible human alternative. Include the played move even when it is outside MultiPV's leading candidates. Use the same root/history, score perspective, and comparable search budgets. Reuse compatible existing searches first. Do not spend a new search merely because the user requested prose.

Choose continuations by explanatory value: capture and recapture sequence, defensive resource, loss of a defender, promotion, king-safety change, or stable positional difference. Replay only legal moves. Never infer that a principal variation is forced merely because the engine supplied it.

Store an evidence record with an ID, type, statement or structured data, position/line scope, origin, supporting line IDs, certainty category, and limitations. Distinguish the statement “the rook attacks a pawn” from the stronger statement “the pawn cannot be saved.”

When deeper coaching analysis disagrees with the reviewed label, use a neutral explanation of the established lines, mark the comparison as unsettled, and offer the existing review-refinement path. Do not generate a confident story justifying a stale label.

**6. Chess feature development order**

| Priority | Feature family | Verification needed |
| --- | --- | --- |
| First | Material changes and exchanges | Replay captures, promotions, and recaptures; count both sides |
| First | Hanging pieces and immediate tactics | Legal captures, defensive replies, compensation checks |
| First | Forks, pins, skewers, discovered attacks | Board geometry plus legality; engine support for claimed payoff |
| First | Best-versus-played comparisons | Comparable searches and meaningful evaluation difference |
| Next | Defense and prophylaxis | Identify a concrete threat and show how the move addresses it |
| Next | Sacrifices | Acceptance/refusal branches and compensation; no invented forced mate |
| Next | Files, rooks, mobility, coordination | Before/after feature changes; avoid claiming causality from correlation |
| Next | Pawn structure, passed pawns, king exposure | Position-specific features and relevant engine comparisons |
| Later | Difficult endgames and deep strategic plans | Dedicated fixtures and deeper analysis where feasible |

Defensive explanations must use legal branches. Do not simulate an illegal “opponent moves again” position to prove a threat. Geometric attacks and hypothetical plans can be represented separately from legal best-play continuations.

Opening names are context, not evidence of why a move is good. Use curated, locally bundled educational concept descriptions only when the position-specific features support them. No web search or external retrieval is needed per explanation.

**7. Groq input, writing prompt, and output**

Use `openai/gpt-oss-120b` as the initial candidate because it is already integrated and currently supports strict structured output. Validate access with an actual Explain request during an explicitly initiated live smoke test. Benchmark before calling it the best choice. Do not silently switch models when unavailable.

The report includes before/after position, readable relevant piece locations, recent moves needed for context, classification, clearly labeled evaluation perspective, selected comparisons, evidence records, and uncertainty. Send enough information to explain the move, not the entire PGN or every legal move. Exclude player names, ratings unless expressly used for a selected level, credentials, and unrelated site content.

The prompt asks the model to explain the central idea first, connect a consequence to its cause, compare alternatives when useful, adapt to the selected level, and use uncertainty appropriately. Prohibit invented variations, unsupported uniqueness/forced-win claims, irrelevant numerical commentary, and generic praise. Treat PGN comments or other user-supplied strings as data, never instructions.

Suggested response shape:

```json
{
  "summary": {"text": "...", "evidenceIds": ["e1"]},
  "comparison": null,
  "lesson": {"text": "...", "evidenceIds": ["e1", "e2"]},
  "lineIds": ["line1"],
  "claims": [
    {"kind": "material_change", "evidenceId": "e2", "lineId": "line1"}
  ]
}
```

Define the full strict JSON schema before coding the adapter. Use required keys with nullable values for optional sections, and `additionalProperties: false` on objects. Bind claims to evidence types and scopes; do not accept arbitrary payloads under a known ID.

Do not request chain-of-thought or display internal reasoning. Request a concise teaching explanation and supporting evidence references. No model tool loop, AI verifier, automatic repair call, or chat history in version one. Perform useful local investigation before the single writing call.

**8. Validation and honest correctness boundaries**

Validate response completeness, refusal status, schema, size, IDs, referenced positions, legal moves, captures, material deltas, and supported terminal claims. Render plain escaped text; do not accept model HTML or executable markup. Reuse only locally stored verified lines for playback.

An evidence citation does not prove that a sentence follows from it. A structured claim list also does not guarantee that the prose contains no additional claim. Validate factual assertions where mechanically possible, flag detectable overclaims, and assess remaining semantic errors through reviewed evaluation fixtures. Do not describe this system as hallucination-proof.

Permit natural paraphrases. Remove the exact-option equality gate. Reject clear contradictions or unsupported concrete tactics; return local feedback and an explicit Retry control. Do not spend another request repairing the output automatically. Strategic statements with limited support should be qualified instead of being falsely certified.

**9. Quota policy and cost control**

Explain-only requests reduce traffic but cannot guarantee avoiding rate limits. Groq quotas also depend on tokens and other use of the same organization. Current published free limits for the initial model are 30 requests/minute, 1,000 requests/day, 8,000 tokens/minute, and 200,000 tokens/day; verify account limits again during implementation. Headers and 429 responses must override assumptions. [Groq limits](https://console.groq.com/docs/rate-limits)

Implement these controls:

- One admitted in-flight coaching request across this extension's review tabs. Coordinate admissions through a trusted broker with persisted short-lived reservations and expiry after crashes.
- Deduplicate by request identity and explanation style, including simultaneous clicks from different tabs. Broker messages contain opaque job identifiers, not credentials.
- Maintain separate request and token accounting with a conservative safety margin. A local ledger is an estimate, not a view of all account activity.
- Count total prompt/schema overhead and reserve plausible completion/reasoning tokens. Start with a compact report target around 1,500 input tokens and a 1,024–2,048 completion-token experiment; select actual settings using truncation and quality measurements. These are tuning targets, not promised usage.
- Reconcile reservations using returned usage and rate-limit headers. If usage is unavailable after abort/timeout, conservatively retain the reservation until its accounting window expires.
- Treat daily and per-minute limits separately. A daily restriction must not become a repeated short retry cycle.
- If capacity is unavailable, show a wait time and keep local feedback available. Do not queue unlimited requests or automatically send one when the timer ends; the user clicks Retry when ready.
- Parse `Retry-After` and reset metadata; use a conservative bounded cooldown when metadata is absent. No automatic backoff request loop.
- Never assume aborting fetch refunds quota or cancels provider computation.
- If other apps consume the same key/account, a 429 can still occur. Handle it as an ordinary recoverable state.

Use HTTP POST to the existing Groq chat-completions endpoint. Configure the adapter for one attempt; ensure any SDK defaults cannot introduce hidden retries. Saving a key does not enable billing or change the provider account plan. Free availability remains controlled by the user's Groq account and provider policy.

**10. Cache, cancellation, and browser lifecycle**

Persist validated explanation results in IndexedDB. Key them by position/history identity, played move, evidence digest, engine/analysis version, prompt/schema version, model, language, and player level. Never include a raw credential in a cache key or store one with an explanation.

Separate explanation content from the credential-scoped quota ledger. Evidence improvements invalidate compatibility without triggering a new provider call. Show local feedback or an explicit refresh action when a previous explanation no longer matches the current analysis. A valid unchanged result should survive reload and return visits.

Provide bounded cache size, least-recently-used eviction, clear-cache controls, schema migrations, and graceful fallback if IndexedDB is unavailable or full.

Cancel preparation when the user navigates away. Immediately before fetch, recheck selection, analysis revision, credential revision, feature state, and quota reservation. For an already submitted request, prevent stale rendering and do not issue a replacement automatically. Abort on key removal/feature disable/page shutdown; preserve conservative quota accounting. Completed valid results may be cached only under their original compatible identity.

Keep workers and long-running operations attached to the review page. Background state must tolerate browser suspension; reservations expire and persistent state is restored. Test Chrome and Firefox/Zen separately. Bundle executable JS/WASM and preserve the existing CSP strategy. The default coach requires neither WebGPU nor a downloaded language model.

Store keys in extension storage accessible through trusted extension code, not webpage localStorage or injected page scripts. Where supported, restrict storage access to trusted contexts. On other supported browsers, enforce the boundary in the extension architecture. Extension storage is not an encrypted secret vault; never claim that it is. Do not log or export keys or authorization headers.

**12. Test and evaluation plan**

Reuse current coaching regressions, especially the queen-loss, sacrifice, Nxb3 equal-exchange, and Raxb3/Rbxb3 examples. Preserve intent while replacing tests that require exact option copying.

Unit tests cover evidence, comparable alternatives, repetition-sensitive identity, score perspective, pins versus legal captures, recaptures, unsupported mate claims, budgets, cache compatibility, header parsing, and reservation expiry. Include Black-to-move and promotions throughout.

Provider simulations cover success with fresh wording, schema violations, supported IDs with false prose, wrong moves/material, truncated output, refusal, 400/401/403/404/429/5xx, delayed responses, missing headers, reasoning-token exhaustion, and network failure. Update the existing Postman Groq mock and coaching simulation when implementing the new contract. Simulations verify client behavior, not live model quality.

Browser tests count requests for every UI action. Test double-clicks, two review tabs, closing a tab mid-job, navigation during local preparation and HTTP, changed evidence, key removal, disabled coach, reload cache reuse, cooldown expiry, and no automatic retries. Keep Stockfish playback and variation regressions independent of the model response. Cover Chrome and Firefox/Zen with actual extension packaging where possible.

Build a benchmark of 200–300 positions across tactical, defensive, quiet, opening, endgame, winning/losing, and ambiguous cases. Start with 30–50 representative cases to stabilize contracts. Separate development examples from a held-out evaluation set. Store FEN plus relevant history, expected findings, acceptable uncertainty, forbidden claims, reviewed supporting lines, and reviewer notes. A fixed engine depth alone is not gold truth.

Proposed release targets, subject to explicit review after pilot measurement:

- 100% of deterministic request-invariant and known regression tests pass.
- No illegal displayed line, false terminal claim, exposed credential, or stale-position explanation in the release suite.
- At least 95% of assessed concrete claims in the held-out sample judged supported, with all severe known errors fixed; report sample size and uncertainty rather than implying a universal guarantee.
- Human-reviewed usefulness at least 4/5 on average, with no move category below 3/5; compare against the current local baseline.
- Record median/p95 local preparation and end-to-end latency, actual token use, fallback rate, truncation rate, and 429 rate on named test hardware. Establish performance thresholds from the pilot, not guesses.

Live quality runs require an explicitly initiated test session and use a small paced sample first. Do not run hundreds of live requests automatically as part of standard tests. No live request is made merely to create this roadmap.

**13. Rollout, observability, and rollback**

Keep the redesign behind a local development feature flag until its gates pass. Rollback should return to working local feedback, not silently select another cloud provider. Migrate stored settings once and invalidate incompatible cache versions.

During development, record local job timings, evidence categories, cache hit/miss, token estimates/actuals, validation outcomes, and request counts. Redact credentials and avoid full sensitive payloads in routine logs. An optional user-exported diagnostic bundle can omit PGN/player data and include only what is necessary to reproduce a reported failure. No remote telemetry service is required.

Document the distinction between local review and cloud explanations, key setup, free-account limitations, supported browsers, cache behavior, error recovery, and evidence limitations. Remove the README claim that the AI selects an exact local option when the new flow ships.

**14. Explicitly deferred scope**

No automatic whole-game cloud explanation, multi-agent cloud analysis, AI-to-AI verification, automatic repair request, shared server API key, subscription backend, browser LLM download, or per-move web retrieval in the initial release.

The earlier idea of a model requesting extra investigations is deferred because it normally requires another model round trip. Version one performs bounded local investigation before its single Groq call. Later follow-up questions must be explicit user actions with visible request semantics; expanding saved text or showing a line remains free of API calls.

**15. Definition of done**

A user can import and review a game, navigate freely, and inspect engine lines without any Groq traffic. Clicking Explain produces local feedback or a cached answer immediately when available; otherwise it prepares relevant evidence and submits at most one quota-admitted request. The result explains the move naturally, presents legal supporting lines, acknowledges genuine uncertainty, and remains useful when the provider is unavailable. Repeated actions do not multiply requests, browser restarts do not destroy compatible cached explanations, and the implementation passes the request, chess, UI, and quality gates above.
